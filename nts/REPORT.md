# NTS 部署评估报告：偏移、抖动与互通

对象：本仓库 `nts`（Rust 实现的 RFC 8915 客户端/服务端）
日期：2026-11-17
环境：macOS 15.5 / Apple Silicon，Rust 1.99，OpenSSL 3.x，chrony 4.9（NTS 支持），网络经本地 NAT 出口

## 1. 结论

1. **双向互通成立，不是"自测通过"**。与 chrony 4.9 的 NTS 服务端、chrony 作为 NTS 客户端、
   以及 Cloudflare 生产 NTS 服务（`time.cloudflare.com`）三条真实路径都完成了完整的
   NTS-KE + 加密 NTP 交换，两种 AEAD 算法各一遍。

2. **NTS 的代价是一次性的，不是每包的**。本机 NTS-KE 中位数 0.70 ms，之后每个 NTP 包只做对称
   AEAD。3000 包无间隔压测下吞吐从 16.7k req/s 降到 12.1k req/s（AES-SIV），约 27%；
   GCM-SIV 约 23%。这是在同一台机器上客户端+服务端各算一次加解密的结果，实际部署中单边只会更低。

3. **NTS 在本机会引入约 +45 µs 的系统性偏移**（表 1）。这不是测量误差，是协议结构决定的，
   原因见 §5。对机房内部 NTP 常见的 ±100 µs 量级目标来说，这个量级需要知道，但不需要修正：
   它远小于 NTS 要解决的秒级/年级时间伪造。

4. **公网抖动受路径主导，NTS 与明文不可分**。Cloudflare 路径（RTT ≈ 200–250 ms）三轮共 900 个
   样本，全部成功。同一轮内 NTS 有时略稳、有时略差，而不同轮之间明文自身就波动了 3.5 ms
   （表 2）。在微秒级协议开销面对百毫秒级路径噪声时，这是预期结果：**不能声称 NTS 提高了公网
   精度，也不能声称它降低了**。NTS 的价值在认证，不在精度。

## 2. 互通矩阵

| 对端 | 方向 | AEAD | 结果 | 证据 |
|---|---|---|---|---|
| chrony 4.9 | 我们的客户端 → 它的 NTS 服务端 | 15 | 通过 | 4/4 响应认证成功，cookie 回补到 8 |
| chrony 4.9 | 同上 | 30 | 通过 | 4/4 响应认证成功 |
| chrony 4.9 | 它的客户端 → 我们的 NTS 服务端 | 15 | 通过 | `measurements.log` 有认证样本，参考 ID `4E545352`（NTSR） |
| chrony 4.9 | 同上 | 30 | 通过 | 同上 |
| Cloudflare | 我们的客户端 → 生产服务 | 15 | 通过 | 3/3、100/100、150/150 响应认证成功 |
| Cloudflare | 同上 | 30 | 通过 | 2/2、100/100 响应认证成功 |
| 本仓库 | 客户端 ↔ 服务端 | 15 / 30 | 通过 | `tests/e2e.rs` 全绿 |

关于 chrony → 我们的方向：chrony 只接受通过 NTS 认证的响应，未认证的响应会被丢弃且不产生
`measurements.log` 条目。因此出现 `4B`（mode 4、基本模式）样本且参考 ID 为我们服务端设置的
`NTSR`，本身就证明认证通过。我们还用 `ntsaeads 15` 和 `ntsaeads 30` 分别强制了两种算法。

**未能完成的互通**：Netnod（`nts.netnod.se`）。本环境的 DNS 被改写到了基准测试网段
`198.18.76.0/15`，该地址在 TCP 4460 上接受连接后不响应 TLS ClientHello；直连 Netnod 的
真实 IP 则被网络策略丢弃。用 OpenSSL 对同一域名做同样握手是成功的，所以可以排除服务端问题，
问题在本环境的出网策略。这一项标记为"未测"，而不是"失败"。

## 3. 偏移与抖动：本机

同一台 chrony 进程同时提供明文 NTP（UDP 12301）与 NTS（TCP 14461 / UDP 12301），
因此两种模式共享服务端实现与网络路径，差异只来自协议本身。每模式 2000 个样本，
请求间隔 5 ms ± 10%。

表 1：本机（回环）

| 指标 | 明文 NTP | NTS / AES-SIV (15) | NTS / GCM-SIV (30) |
|---|---|---|---|
| 样本数（失败） | 2000 (0) | 2000 (0) | 2000 (0) |
| 偏移 \|均值\| | 3.9 µs | 51.8 µs | 47.9 µs |
| 偏移 标准差 | 6.3 µs | 15.2 µs | 13.3 µs |
| 偏移 抖动（RFC 5905 §11.4） | 8.8 µs | 21.2 µs | 18.7 µs |
| 往返时延 均值 | 82 µs | 190 µs | 190 µs |

"抖动"是相邻样本差值均方根（RFC 5905 的定义），衡量采样间噪声；"标准差"衡量相对均值的离散。
两者都列出，因为它们回答不同的问题：前者决定时钟滤波器要滤掉多少噪声，后者决定均值有多可信。

**吞吐**（3000 包、无间隔、客户端与服务端同机）：

| 模式 | req/s | 占比 | 平均 RTT |
|---|---|---|---|
| 明文 | 16.7k | 100% | 28.0 µs |
| NTS / 15 | 12.1k | 72% | 32.9 µs |
| NTS / 30 | 11.7k | 77%（相对该轮明文） | 39.6 µs |

## 4. 偏移与抖动：公网

`time.cloudflare.com`，NTS-KE 走域名解析，NTP 走其 anycast 地址 `162.159.200.1`
（本环境 DNS 解决了 KE 的 TCP 连接，但注入的 NTP 地址不可达，故显式指定。这不影响 NTS 本身：
服务端在 NTS-KE 响应里没有下发不同的 NTP 地址，cookie 与 anycast 地址是配套的）。

表 2：公网（Cloudflare，RTT ≈ 200–250 ms）。四组独立运行，全部 0 失败。

| 运行 | 模式 | 样本 | 偏移 \|均值\| | 偏移 标准差 | 偏移 抖动 | 往返 均值 |
|---|---|---|---|---|---|---|
| A | 明文 | 100 | 87.0 ms | 11.2 ms | 16.2 ms | 219.8 ms |
| A | NTS / 15 | 100 | 82.5 ms | 8.1 ms | 9.1 ms | 220.9 ms |
| B | 明文 | 100 | 79.3 ms | 18.6 ms | 19.7 ms | 230.4 ms |
| B | NTS / 30 | 100 | 83.0 ms | 17.7 ms | 21.5 ms | 230.4 ms |
| C | 明文 | 150 | 93.6 ms | 20.5 ms | 19.2 ms | 250.5 ms |
| C | NTS / 15 | 150 | 90.2 ms | 23.2 ms | 26.1 ms | 250.6 ms |

读法：先看同一轮里明文与 NTS 的差，再看不同轮之间明文的差。

* 轮 A：NTS 抖动更小（9.1 vs 16.2 ms）。
* 轮 B：NTS 抖动略大（21.5 vs 19.7 ms）。
* 轮 C：NTS 抖动略大（26.1 vs 19.2 ms）。

而明文自己在三轮之间的抖动就覆盖了 16.2–19.7 ms 的范围。结论是：**在 200 ms 级公网路径上，
路径噪声压倒协议差异，NTS 与明文的偏移/抖动没有可分的高低**。NTS 的即时额外开销（加解密）
在微秒级，相对 200 ms 的路径抖动可以忽略；轮 A 中 NTS 更"稳"只是路径在那两分钟里更平静。
不应从这些数据声称 NTS 提高或降低了公网精度。

NTS-KE 耗时在轮 A/B 约 1.36–1.4 s，绝大部分是本地注入 DNS 解析与 200 ms RTT 的往返，
不是握手本身；本机同一握手是 0.7 ms（§3）。

## 5. 为什么本机有 +45 µs 偏移

服务端的时间戳是这样取的：

```
收到请求       → receive_ts = now()          (t2)
验证 cookie 并解密、验签  ← 这段时间没被计入
生成响应       → transmit_ts = now()          (t3)
```

RFC 5905 的偏移公式 `((t2−t1)+(t3−t4))/2` 假设服务端在 t2 与 t3 之间不做耗时工作。NTS 在这
之间多了一次 AEAD 验签与一次 cookie 解密，于是 t3 被推后，而 t2 不变，两项平均后偏移向
"本地落后"方向偏大约半个处理时长。实测约 45 µs，与一次 AES-SIV 验签加一次 cookie 解密的
量级相符。

这是所有 NTS 实现共有的性质，不是本实现的缺陷。两个可以做的改进（均未在本次实现）：

* 把 t3 取在"验签完成、开始构造响应"之前，而不是之后，可消掉大部分；
* 或用网卡/内核收包时间戳（`SO_TIMESTAMPNS`）替代用户态取样。

在生产中这个量级通常被服务端与客户端之间几毫秒的 RTT 与路径不对称掩盖；只有在回环或
同机房低噪声链路上才会显现成系统性偏差。

## 6. 安全性质（本次实测的相关部分）

* 篡改任一个被认证的头字段或扩展字段，客户端拒绝。见 `tests/e2e.rs::tampered_server_response_is_rejected`。
* 明文 NTP 响应永远到不了客户端：没有认证器，`verify_response` 在接触时间戳之前就返回错误。
  见 `tests/e2e.rs::unauthenticated_reply_never_reaches_the_client`。
* 主密钥轮转后，旧 cookie 在保留期内继续可用，超出后被拒绝并触发 NTS NAK，客户端自动重跑
  NTS-KE 恢复。见 `tests/e2e.rs::cookies_survive_a_single_rotation_and_then_expire`。
* 相同种子启动的两个服务端实例互相接受对方签发的 cookie，轮转后仍同步，所以无状态横向扩展
  不需要共享存储。见 `seed_determinism_across_server_instances`。
* 一个 cookie 只用于一次请求；服务端每次响应回补，客户端库存稳定在 8，25 次轮询不必重跑
  NTS-KE（`client_uses_each_cookie_once`、`full_session_with_both_algorithms`）。

## 7. 已知局限

* Netnod 未能互通，原因在本文档所述网络环境，非实现问题（§2）。
* 服务端不 disciplining 本机时钟，只报告自己的时间，供客户端比对。
* 未实现 RFC 8915 §5.7 建议的客户端 cookie 持久化缓存（重启后需重跑 NTS-KE）。
* 未实现 NTS-KE 服务端限速（chrony 有 `ntsratelimit`，本次未做）。
* 服务端未对 IPv6 与多监听地址做绑定（命令行只接受一个 `--ntp` / `--ke`）。

## 8. 复现

```sh
# 构建
cargo build --release

# 本机对照（chrony 需同时开明文与 NTS；见仓库 scripts/）
./target/release/nts-bench --mode both \
    --server 127.0.0.1:14461 --ntp 127.0.0.1:12301 \
    --ca ca.crt --count 2000 --interval 0.005 --aead 15 --json

# 公网
./target/release/nts-bench --mode both \
    --server time.cloudflare.com --ntp 162.159.200.1 \
    --count 100 --interval 0.3 --aead 15 --json
```

`--json` 输出每个样本的偏移与延迟，可自行重算统计量。
